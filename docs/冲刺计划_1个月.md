## 1. 这台机器能不能扛：内存账

2G = 2048 MB。逐项压：

| 组件 | 常驻 | 峰值 | 调参手段 |
|---|---|---|---|
| 系统 + sshd + cron | 150 | 150 | 关掉无用服务（postfix、bluetooth 等） |
| Docker daemon + containerd | 120 | 120 | 只装一个引擎，不开 swarm |
| MySQL 8.0 | 380 | 500 | 见下方参数 |
| Redis 7 | 55 | 128 | `maxmemory 128mb` |
| api（Go） | 80 | 260 | PDF 解析时峰值 |
| worker（Go） | 80 | 260 | 同上 |
| Nginx | 15 | 15 | — |
| **合计** | **880** | **1433** | 剩 600 MB 给页缓存，**够但不宽裕** |

### 1.1 MySQL 必须改的参数

默认配置在 2G 机器上会吃掉 700MB+。`deploy/mysql/my.cnf`：

```ini
[mysqld]
innodb_buffer_pool_size = 256M     # 默认 128M，但 500 条法条+200 份合同，256M 够
innodb_log_file_size    = 64M
innodb_flush_method     = O_DIRECT  # 绕过页缓存，省内存
innodb_flush_log_at_trx_commit = 2  # 牺牲 1s 持久性换 IO；本校项目可接受
max_connections         = 50        # 默认 151，2 核用不上
performance_schema      = OFF       # 省 200MB，本项目不需要
table_open_cache        = 200
skip_name_resolve       = ON        # 省 DNS 查询
character_set_server    = utf8mb4
collation_server        = utf8mb4_0900_ai_ci
```

> `innodb_flush_log_at_trx_commit=2` 是有代价的：断电可能丢最后 1 秒事务。**答辩场景可接受，写进 runbook 的已知取舍。**

### 1.2 Redis 必须改的参数

```conf
maxmemory 128mb
maxmemory-policy allkeys-lru
save ""              # 缓存不需要 RDB，省 fork 内存
appendonly no
```

### 1.3 Go 进程必须设的上限

```dockerfile
ENV GOMEMLIMIT=350MiB   # 软上限，触发更积极的 GC
ENV GOGC=100
```

容器再加硬限：

```yaml
deploy:
  resources:
    limits:
      memory: 512M      # api
    reservations:
      memory: 128M
```

**关键**：`GOMEMLIMIT` 比容器 `limits` 低 150MB，让 Go 在容器 OOM 之前先自己回收，否则会看到"进程被 kill 但日志里没有任何错误"——这是 2G 机器上最难查的一类故障。

### 1.4 必须开 swap

2G 内存跑上面这套，页缓存会被挤空，一次大 PDF 解析就可能触发 OOM Killer。加 2G swap 云盘：

```bash
fallocate -l 2G /swapfile && chmod 600 /swapfile
mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
sysctl vm.swappiness=10     # 低值：优先用物理内存，实在不够才换
```

swap 不是性能方案，是**防猝死**。落在 SSD 云盘上，偶尔换出不影响 SSE。

### 1.5 实测判定标准

部署完跑一次全链路，然后：

```bash
free -m                 # available 必须 > 300MB
docker stats --no-stream  # 每个容器 RSS
```

如果 `available` 长期 < 200MB，说明有一个组件超预算，按"MySQL → api → worker"顺序查。

## 2. 带宽：这是必须花钱的一关

图片里写的是"无带宽，带宽不抵券"——**这台机器现在没有任何公网出口能力**。

| 方案 | 价格（华东1，1 个月） | 适用 | 取舍 |
|---|---|---|---|
| **固定带宽 1 Mbps** | ¥23/月 | 平时开发 + 演示 | 够跑 SSE（文本流每秒几十 KB）；但 5MB PDF 上传约 40 秒 |
| 固定带宽 5 Mbps | ¥125/月 | 演示当天 | 上传 5MB 约 8 秒，演示体感正常 |
| 按使用流量 | ¥0.8/GB | 访问量极小 | 上传下载多了不划算，且无法预估 |

**我的建议**：平时买 **1 Mbps 固定**（¥23），演示前 1 小时临时升到 **5 Mbps 按小时计费**（约 ¥0.17/小时）。阿里云控制台"变更带宽"支持临时升配。

### 2.1 未备案的硬坑

阿里云大陆节点的公网 **80 / 443 端口必须备案**，否则被阻断。两条路：

| 路 | 做法 | 风险 |
|---|---|---|
| **A（推荐）** | 用 **8443 端口** + IP 直连：`https://<公网IP>:8443` | 部分企业/校园网络会拦非标端口；演示前务必在学校网络上实测一次 |
| B | 买香港/新加坡节点（免备案） | 延迟 40–80ms，SSE 首字节指标会变差；且这台已经买在大陆 |
| C | 域名 + 备案 | 备案要 7–20 天，**一个月内来不及** |

**行动项（今天就要做）**：在阿里云控制台确认实例地域，然后决定 A 还是 B。如果是大陆节点，直接用 8443，别再折腾备案。

## 5. 一个月版的三个最大风险

| 风险 | 概率 | 后果 | 应对 |
|---|---|---|---|
| **2G 内存 OOM** | 高 | 演示中途服务重启 | W4 D1 就压测，别等到最后；`GOMEMLIMIT` 必设；PDF 解析并发锁 1 |
| **B 的 Agent 进度** | 高 | 咨询/审查二选一都上不了 | W1 就用 FakeClient 并行开发，A 不被 B 阻塞；B 每 2 天必须能跑通一个 graph 节点 |
| **未备案端口被封** | 中 | 公网演示打不开 | 今天确认地域；用 8443；演示前在校园网实测；备用方案：本机 + frp 隧道 |

**最小可交付底线**（万一全崩）：本地 `go run` + 前端 `pnpm dev` 跑给对方看，云上只作为"部署能力"的截图证据。这比"云上挂了演示不了"强。

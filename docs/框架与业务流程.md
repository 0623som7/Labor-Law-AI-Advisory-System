## 一、框架：怎么分层

### 1.1 全景图

```
                    浏览器（Vue 3 + Pinia + PDF.js）
                              │  HTTPS：JSON 接口 / SSE 长连接
                              ▼
┌──────────────────────────────────────────────────────────────┐
│ cmd/api  —— 装配根（整个项目只有这里同时认识所有包）           │
│   .env → config.Load() → 连 MySQL/Redis → api.New() → Serve    │
└──────────────────────────────────────────────────────────────┘
                              │
        ┌─────────────────────┼──────────────────────┐
        ▼                     ▼                      ▼
  internal/api          internal/store          internal/llm      ← A 提供
  （接口层：翻译HTTP）   （数据层：SQL/迁移）      （模型层：调上游）
        │                     ▲                      ▲
        │                     │                      │
        ▼                     │                      │
  internal/agent  ────────────┴──────────────────────┘             ← B 提供
  （编排层：consult / qa / review 三条流程）
        │
        ├── internal/prompt        prompt 模板与版本
        ├── internal/extract       合同要素抽取
        ├── internal/rules         20 条规则引擎
        └── internal/retrieval     法条检索
        │
        └── 只能通过 internal/port 说话（唯一契约包，不含实现）
```

把这张图读成一句话：

> **main 把所有零件装起来；api/agent 是两种"上层"，llm/store 是被它们共用的"下层"；port 是它们之间签的合同。**

### 1.2 四条分层规则

| 规则 | 具体是什么 | 违反了会怎样 |
|---|---|---|
| ① 依赖单向 | `api` 不 import `agent`，`agent` 不 import `api`，双方只 import `port` | 循环依赖 → Go 编译直接报 `import cycle not allowed` |
| ② 装配只在 main | 只有 `cmd/api/main.go` 同时认识 config / store / api / llm | 每个包自己 new 依赖 → 测试时没法替换成假实现 |
| ③ 接口在 port，实现在各自包 | `port.Client` 定义"能调模型"，`internal/llm` 实现它 | B 直接 import `internal/llm` → 两人改同一份代码，并行失效 |
| ④ 每层只干一件事 | 见下表 | 层次模糊 → 改一条规则要读五个包 |

### 1.3 每层只干一件事

| 层 | 干什么 | 明确不干什么 | 证据（注释原文位置） |
|---|---|---|---|
| `internal/api` | 把 HTTP 翻译成 port 调用；错误翻译成状态码；结果套包络 | 不写业务规则 | `api.go:3-5`「业务规则一行都不写在这里」 |
| `internal/agent` | 编排：调模型、查法条、跑规则、发事件 | 不碰 HTTP、不碰 PDF、不写 SQL | `port/doc.go:15`、`agent.go:59-61` |
| `internal/llm` | 选模型、超时、重试、限流、计量、成本闸 | 不决定 prompt 内容 | `llm.go:31-32`「五件事必须只有一个地方做」 |
| `internal/store` | SQL、事务、迁移、驱动错误包装 | 不判业务、不做权限判断 | `store.go:12-13` |
| `internal/port` | 定 interface、DTO、错误码 | 不含任何实现、不 import 具体库 | `doc.go:3-4` |

### 1.4 谁提供 / 谁消费（这是 A、B 分工的账本）

| 契约 | 谁实现 | 谁调用 | 一句话 |
|---|---|---|---|
| `port.Client`（146 行） | **A**（`internal/llm`） | B | B 唯一允许的模型出口；重试/限流/计费都在这后面 |
| `port.Runner`（136 行） | **B**（`internal/agent`） | A | A 把请求丢进去，B 通过 `emit` 一帧帧吐事件 |
| `port.Store`（174 行） | **A**（`internal/store`） | B | 按域分组：Session/Message/File/Review/Statute/Task + Tx |
| `port.ParsedDoc`（107 行） | **A**（`internal/file`） | B | PDF 解析后的纯数据（带 pt 坐标），B 拿不到 PDF 本体 |
| `port.Handler`（20 行） | A 定义 / **B 注册** | A 的协程池 | 异步任务函数；并发/超时/重试由 A 管，B 不准自己起 goroutine |

记住一句话就够：**A 提供"手和脚"（调模型、读写库、解析文件），B 提供"脑子"（怎么问、怎么判）。**

### 1.5 现在的装配缺口

`cmd/api/main.go` 现在装配了 `config`、`store`（`NewWithSecret` 聚合体）、`storage`、`file`、`retrieval`、`agent` 与 `api`（含 `stream.Hub`）。`llm` 不单独出现在 main 里：`cmd/api/runner.go` 把它塞进 `agent.New(llm.New(cfg.LLM, ...), ...)`，和检索器一起交出去。
**`internal/worker` 与审查 handler 的装配还没进 main**：`cmd/**` 是 AI 禁区，仓库里已经给出确切的补丁（`pool := worker.New(...)`、`pool.SetProgressSink`、`agent.NewReviewHandler`、`api.WithTaskSubmitter/WithReviewHandler`），要由责任人粘进 `cmd/api/main.go`。粘之前，同一套装配已经在 `.dev/smoke/main.go`（本地验收宿主，不进仓库）里端到端跑通过，参数完全一致。

```
main.go 现在：  config ──→ store ──→ storage ──→ file ──→ retrieval ──→ agent（内含 llm）──→ api（chat/files/statutes/reviews/tasks/sessions 全部真实现，501 清零）
main.go 应该：  config ──→ store ──→ storage ──→ file ──→ retrieval ──→ agent ──→ worker ──→ api（审查链路接 worker）
```

## 二、逻辑：两条业务链路

所有接口都挂在 `/api/v1` 下，除注册/登录/续期外都要令牌。现在 23 条 API 路由全部有实现，`501` 已清零（会话 5 条于 `2f9b6b7` 落地）。`/chat/completions` 背后是真实的 `agent.Runner`：先检索法条、把原文拼进系统提示词、再流式生成，引用只从库里取（`256a201` / `ba1fd33`）；4 条 `/files` 能真正上传、解析、取坐标、下载；2 条 `/statutes` 能按口语检索与按 ID 取原文；6 条 `/contracts/review` + `/reviews` + `/tasks` 能建任务、轮询进度、取风险清单（`4f2f68d` + `8226608`，本地实测 8 条 finding）。
所以下面的链路是**设计好的完整路径**，标了每步当前状态。

### 2.1 链路一：劳动法咨询（流式）

用户输入「公司让我试用期三个月，合法吗」，系统边生成边推字。

| 6 | 取历史消息（最近 N 条）拼上下文 | A | `store.Message().ListBySession` | ✅ `62f1675`（`newHistory` 注入 `agent.WithHistory`） |

两条不能破的约定（写在 `port/agent.go` 里，违反了会出线上事故）：

- **delta 和 done 绝不能丢**，`tool_call` 可以丢；`emit` 单次阻塞不许超过 100ms（否则背压把连接拖死）。
- **一旦已经开始吐字，就不许重试**——重试会把前半段推两遍，用户看到重复句子而日志完全正常。

### 2.3 把两条链路抽象一下

其实所有业务接口都是同一个五段骨架，看懂了这五段就等于看懂了全部代码：

```
① 进来     中间件：trace_id 打标 → 访问日志 → 鉴权（谁在调用）
② 查上下文 store：会话属于这个用户吗？历史消息？文件解析过了吗？
③ 干活     Runner.Run(...)  ← B 的编排，内部可能调很多次 llm.Client
④ 吐结果   流式：一帧帧 SSE；同步：一个 JSON；异步：先给 task_id 再轮询
⑤ 收尾     落库（messages / reviews / findings / usage_records）+ 回执
```

区别只在 ④：咨询是流式，审查是异步任务，普通查询是同步 JSON。

### 2.4 两个状态机（看懂这两张，异步逻辑就不会乱）

```
task:   pending ──→ running ──→ succeeded
                     │   │
                     │   └──→ failed（可展示的原因文案）
                     └──→ cancelled（用户取消）

review: pending ──→ running ──→ succeeded / failed
```
非法转移由 `store` 返回 `CodeConflict`（比如 pending 直接跳 succeeded）；
进程崩溃时 `TaskStore.FailRunning` 在启动时把所有残留 `running` 标成 failed——否则永远没人接手。

## 三、数据怎么串起来（ER 人话版）

14 张表，按"用户 → 用起来"的顺序看：

```
users ──1:N── sessions ──1:N── messages            ← 咨询链路
  │
  └──1:N── files ──1:N── file_pages ──1:N── text_blocks   ← 上传与解析（坐标在这）
                 └──1:1── contract_extracts               ← 抽出来的要素
  │
  └──1:N── reviews ──1:N── findings                       ← 审查结果（bbox 在这）
                 └──1:1── tasks (review.task_id)          ← 异步进度

statutes / cases / embeddings   ← 只读知识库（全量重建，不做单条改）
usage_records                   ← 每次模型调用的账（日成本闸的数据源）
```

四个跨表一致的约定（都在 `0001_init.up.sql` 第 3–7 行）：

| 约定 | 值 | 为什么 |
|---|---|---|
| 主键 | `CHAR(26)` ULID | 带时间前缀 → `ORDER BY id` 就是时间序；不暴露"你是第几个用户" |
| 时间 | `DATETIME(3)` 存 UTC | 地方政策有生效日期，毫秒够用；统一时区避免算错天数 |
| 长文本 | `MEDIUMTEXT` | 合同原文、法条正文很长，别混在业务列里 |
| 索引 | 每张表只建"有查询对应"的索引 | 没有查询支撑的索引只带来写放大 |

## 四、六个机制，每个一句话

| 机制 | 一句话 | 落在哪 |
|---|---|---|
| **统一包络** | 所有响应都是 `{code,message,data,trace_id}`，前端只认这一种形状 | `api/response.go` |
| **错误码 + 可重试标记** | 14 个业务码；`Code.Retryable` 决定 worker 要不要重试（`AppError` 最多 2 次，普通 error 一律不重试） | `port/errors.go`、`worker.go:13-15` |
| **trace_id 全链路** | 每个请求一个 ID，日志、响应、usage_records 都带它，排错靠它串 | `api/middleware.go`、`TraceID(c)` |
| **配置启动即校验** | 44 个键一次性校验，缺了直接起不来；报错只报变量名不报值（值里有 DSN 和 key） | `config/config.go` |
| **迁移在程序里** | 建表不手敲，`AUTO_MIGRATE=true` 或 `-migrate` 跑；生产禁自动迁移，schema 变更要人工确认 | `store/migrate.go` |
| **并发收敛在池里** | 所有耗时任务走 `internal/worker` 固定大小池子；B 不准自己起 goroutine | `worker.go:18-19` |

## 附：三层类比（零基础版）

把整个系统当成一家小餐馆：

| 餐馆 | 本项目 |
|---|---|
| 门面与点菜台 | `internal/api`：接单、检查你有没有会员卡（鉴权）、把单子转成内部单号（trace_id） |
| 厨师长 | `internal/agent`（B）：看单子决定先炒什么、要不要查配方；他自己不下厨 |
| 灶台与采购 | `internal/llm`（调外部供应商）、`internal/store`（仓库取料） |
| 仓库账本 | MySQL 14 张表 / Redis 缓存 |
| 传菜窗口 | SSE：菜做好一部分就端出去一部分（不是整桌做完才上） |
| 店规 | `internal/port`：谁负责哪块、怎么交接、出错怎么报 |
| 老板 | `cmd/api/main.go`：只在开张和打烊时出现（装配与优雅关闭） |

出错时先问"是点菜台、厨房、还是仓库的问题"——这就是排查顺序，也是日志里 trace_id 的作用。

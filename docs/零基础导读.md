## 1. 一句话：这东西是干什么的

**一个只懂劳动法的 AI 顾问网站**，两个场景共用一套底座：

| 场景 | 用户动作 | 系统给你什么 |
|---|---|---|
| 咨询（consult） | 打字问「试用期三个月合法吗」 | 逐字流式回答 + **每条结论挂着法条原文**（可点开核对），不算经济补偿、不编法条 |
| 审查（review） | 传一份劳动合同 PDF | 风险清单（高/中/低）+ 每条风险**指向合同里哪一句话**，点一下就高亮原文 |

答辩时的 10 分钟演示动线就是这两条串起来：

```
注册登录 → 问一个劳动法问题 → 答案逐字出现、旁边挂法条卡片
       → 传劳动合同 PDF → 看到风险列表 → 点一条风险 → PDF 上高亮那行字
```

为什么值得做：普通人遇到"公司不给加班费""试用期随便辞退"，缺的不是法条（网上都有），
而是**不知道自己这种情况算不算违法、能要多少钱、该找谁**。这个项目的卖点不是"会聊天"，
是**每句话都能追到法条**——`docs/项目大纲与技术选型.md` §1.3 把这条写成硬指标：
"引用可信：回答里每条法条引用都能追溯到库内条文，零编造"。

## 2. 为什么代码长成这样：三条硬约束

看懂这个仓库，比看懂任何一个函数都重要的是先记住三条约束。仓库里那些"看起来奇怪"的选择，全是它们逼出来的。

**① 两个人，一个后端一个 Agent —— 所以有了 `internal/port`**

A 写后端（HTTP、数据库、部署），B 写 Agent（调大模型、抽合同要素、判规则）。
两个人同时改一个 Go 项目，最容易死在"你改的接口我不能编译"。
于是先定了一份**合同**：`internal/port` 里只有 interface 和数据结构，没有一行实现，谁都不许往里塞 gin、sqlx、redis 的依赖。
A 照着这份合同写实现，B 照着这份合同写调用，两边互不阻塞。
→ 这就是代码里反复出现的 `port.Client` / `port.Runner` / `port.Store`。**先读 `internal/port/doc.go`（38 行）**，它是整个仓库的总纲。

**② 一个月从零到能演示 —— 所以有 501 占位和无情的砍单**

`internal/api/scaffold.go` 里的 `notImplemented` 让 11 条接口现在仍返回 `501 接口尚未实现`（认证五条、`/chat/completions`、4 条 `/files`、2 条 `/statutes` 已经换成真实现：23 条 API 路由里 12 条能干活）。
为什么不干脆不注册？因为 404 在联调时会被误判成"路径写错了"，501 明确表示"路由在、实现没接"。
砍单同理：判例推荐、维权时间轴、报告导出 PDF 全部砍掉，`docs/冲刺计划_1个月.md` §4 逐条写了理由。
**验收看的是闭环能不能走通，不是功能多不多。**

**③ 服务器 2 核 2G、套餐不含带宽 —— 所以架构是"反潮流"的**

| 常见做法 | 这个项目 | 原因 |
|---|---|---|
| 微服务 + 消息队列 | 单进程 `cmd/api`，worker 内嵌 | 2G 内存装不下第二套运行时 |
| Milvus / Elasticsearch 做检索 | 法条用 MySQL `LIKE` + ngram | 500 条法条用向量库是杀鸡用牛刀，2G 也装不下 ES |
| 公有云托管数据库/Redis | 同机 Docker 起 MySQL 8 + Redis 7 | 预算 5000 元是全部经费 |
| 80/443 直接开 | 走 **8443** | 域名未备案，80/443 会被阻断 |

记住这张表，你就理解了为什么这个项目"看起来不像大厂架构"——**它是被资源逼出来的最小可行形态**。

## 4. 一个请求在代码里怎么走

以"查健康状态"为例（这条现在真的能跑通），理解完整链路：

```
你在终端敲 curl http://127.0.0.1:8080/healthz
        │
        ▼
cmd/api/main.go:86   http.Server{ Addr, Handler: api.New(...).Handler(), 各种超时 }
        │            ← 这里是整个程序唯一的"服务器"，一个进程一个
        ▼
internal/api/routes.go:19   r.Use(recovery, traceID, accessLog)
        │            ← 中间件 = 洋葱皮，请求穿过三层才到业务代码
        │              recovery：接住 panic 不让进程崩
        │              traceID：给这次请求一个 ID，日志里能串起来
        │              accessLog：请求结束后记一行日志（状态码+耗时）
        ▼
internal/api/routes.go:22   r.GET("/healthz", a.handleHealthz)
        ▼
internal/api/health.go     返回 {"status":"ok"}，不查数据库
        ▼
cmd/api/main.go  信号（Ctrl+C / SIGTERM）→ 停止接新请求 → 等在途请求完成 → 退出
```

再看"业务请求"现在长什么样（以创建会话为例）：

```
POST /api/v1/sessions
  → accessLog 打日志
  → v1.Group("") 没有额外中间件
  → authed 组 挂 requireAuth（scaffold.go:32）
       有 AUTH_DEV_USER 就直接放行（开发期偷懒用），没有就 401
  → a.notImplemented("创建会话")（scaffold.go:16）
  → 返回 501 {"code":50001,"message":"创建会话接口尚未实现","trace_id":"..."}
```

**关键点：所有响应都是同一个信封**（`internal/api/response.go`）：

```json
{ "code": 0, "message": "ok", "data": {...}, "trace_id": "abc123" }
```

前端只认这一种形状，出错看 `code`（14 个业务码定义在 `port/errors.go`），排查看 `trace_id`。
这就是为什么很多文件注释里写着"不写业务规则"——HTTP 层只做**翻译**：HTTP 请求 → port 调用；错误 → 状态码。

**SSE 流式回答**（`/chat/completions` 现在已经能吐字）本质上是同一条链路，只是响应不再是"一次性 JSON"，
而是一条一直开着的管道，服务器分批写：

```
event: meta      {message_id, model}
event: delta     逐字 "试用期"
event: delta     "的约定…"
event: citation  {statute_id, 原文}
event: done      {usage, finish_reason}
```

浏览器拿到一帧就渲染一帧，所以用户看到"字一个个蹦出来"。这也是为什么 `HTTP_WRITE_TIMEOUT` 必须是 0——
任何写超时都会在回答到一半时把管道掐断，而且日志里看不到错误（记住这条，将来它一定会咬你一次）。

## 5. 七个必须懂的概念（每个都落到本项目的文件）

| 概念 | 一句人话 | 在本项目哪里 |
|---|---|---|
| **进程 / 端口** | 一个跑起来的程序占一个门牌号，`curl` 就是敲门 | `cmd/api/main.go` 的 `http.Server{Addr}` |
| **HTTP + 状态码** | 请求-应答的格式；200 成功、401 没登录、501 没实现、500 内部错 | `internal/api/response.go`、`scaffold.go` |
| **中间件** | 业务代码之前的一道道关卡，每道可以放行、改写、或直接拦下 | `internal/api/middleware.go` |
| **interface / 依赖注入** | 先约定"要什么能力"，再决定"谁来提供"，这样 A 和 B 可以同时干活 | `internal/port/*.go` 全是 interface；`api.New(cfg, log, checkers...)` 就是注入 |
| **配置** | 代码不变、行为可变的那些值；本项目的原则是"启动即校验，缺一个就起不来" | `internal/config/config.go`（464 行）+ `.env` |
| **数据库迁移** | 建表不手敲 SQL，而是仓库里存一串编号的 SQL 文件，程序启动时按顺序补跑 | `internal/store/migrate.go` + `migrations/0001_init.up.sql` |
| **context / 优雅关闭** | 每个请求带一个"可取消的手柄"；收到 Ctrl+C 时先停止接客，把手上的活干完再退 | `main.go:60` `signal.NotifyContext`、`serve()` |

再补两个后面会用到的：

- **goroutine**：Go 里的"轻量线程"。并发解析 PDF、并发调模型都靠它，但**必须有上限**（2 核机器上开一千个只会一起变慢）。`internal/worker` 的协程池就是干这个的。
- **坐标系统**：PDF 里的位置用 pt（1/72 英寸）、原点在左下、y 轴向上；浏览器画布原点在左上、y 轴向下。两套坐标只能在一个地方换算（`web/src/utils/pdf/coords.ts`），否则标注全错位。

## 7. 自己验证"它还活着"的四条命令

在本仓库根目录跑（PowerShell 也行，Git Bash 也行）：

```bash
# 1. 能编译（最便宜的体检，2 秒）
go build ./...

# 2. 全部单测（15 个包、245 个测试函数，约二十秒）
go test ./...

# 3. 起服务，然后另开一个终端敲门
go run ./cmd/api
curl http://127.0.0.1:8080/healthz      # 期望 {"status":"ok"}
curl http://127.0.0.1:8080/readyz       # 期望 200 且 checks 里 mysql/redis 都 ok
curl -i http://127.0.0.1:8080/api/v1/sessions      # 期望 401（没带令牌）
curl -i -X POST http://127.0.0.1:8080/api/v1/sessions  # 期望 501 + trace_id

# 4. 本地数据库（前台窗口跑，别关）
powershell -ExecutionPolicy Bypass -File .\scripts\dev-mysql.ps1 start
```

看日志：每行都有 `trace_id`，把 curl 返回的那串 ID 拿去搜日志，就能看到这次请求走过哪些层。
**这一步很重要**：以后排查"为什么这个接口报错"，靠的就是 trace_id 串起来的那几行。

## 8. 读代码的推荐顺序（别从 main.go 顺着往下读）

零基础最容易犯的错是从第一行读到最后一行。Go 项目按**依赖方向**读才不会迷路。

| 顺序 | 文件 | 行数 | 读的时候只问一个问题 |
|---|---|---|---|
| 1 | `internal/port/doc.go` | 38 | 这个项目分给谁什么活？ |
| 2 | `internal/port/llm.go` + `agent.go` | 146+136 | A 和 B 之间到底传什么？ |
| 3 | `contract/openapi.yaml` 开头 200 行 | — | 对外暴露哪些接口、每个参数什么意思？ |
| 4 | `cmd/api/main.go` | 282 | 程序从启动到退出，按顺序做了哪几件事？ |
| 5 | `internal/api/routes.go` | 89 | URL 是怎么映射到函数的？ |
| 6 | `internal/api/response.go` | 73 | 成功和失败分别长什么样？ |
| 7 | `internal/config/config.go` | 500 | 44 个配置项都在管什么？（只读结构体和 Validate） |
| 8 | `migrations/0001_init.up.sql` | — | 14 张表各存什么，怎么连起来？（先看 `users/sessions/messages` 三张） |
| 9 | `internal/llm/llm.go` | 317 | 一次模型调用经历了哪几步：选模型→限流→重试→计量→成本闸 |
| 10 | `internal/llm/fake.go` | 105 | 没有 API key 时怎么假装有一个模型？ |

读每一段时如果看到看不懂的注释，那通常是**踩过的坑**（比如"流式一旦吐字绝不重试"），
这些注释比代码本身值钱，它们是决策记录。看不懂就直接来问我，我按"它在防什么事"来讲。

## 9. 两个窗口怎么分工

- **开发窗口**：写代码、跑测试、提交。那边出活。
- **这个窗口（讲解）**：只做理解类工作——讲架构、讲某段代码为什么这么写、解释报错、画流程、给学习路径。**默认不动代码**（除非你明确说"改"）。

最省事的问法（越具体越好）：

| 你想知道的 | 直接这么问 |
|---|---|
| 这个概念是啥 | 「SSE 是什么，用生活里的事打个比方，然后说它在我们代码哪个文件」 |
| 这段代码看不懂 | 「把 internal/llm/llm.go 的 ChatStream 逐行讲，我要知道每行为什么存在」 |
| 报错不懂 | 「贴报错原文 + 我在跑什么命令」→ 我先判这层是哪层的问题 |
| 想知道整体 | 「把审查链路从上传到出风险清单，画成图，标出每一步在哪个文件、谁负责」 |
| 想学某个技术 | 「MySQL 迁移机制讲透，从原理到我们自己怎么用」 |
| 不知道该问什么 | 「我现在该学什么，按这个项目的需要排个顺序」 |

我默认按四层讲：**原理 → 组成 → 流程 → 具体到文件与代码**。哪层听不懂就说"停在第几层"。

## 附：最容易混淆的三组词

| 词 | 别搞混 |
|---|---|
| `port` vs `internal/llm` | `port` 是"要什么能力"（interface），`llm` 是"怎么做到"（实现）。前者归两人共有，后者归 A |
| 迁移（migration） vs 建库 | 迁移是**版本化的建表脚本**，`docker compose up` 不会自动建表，`AUTO_MIGRATE=true` 或 `go run ./cmd/api -migrate` 才会 |
| 501 vs 500 | 501 = "接口在这儿，但还没实现"（预期内）；500 = "实现了但崩了"（预期外）。看到 501 不是 bug |

## 复现方式

```bash
DSN="laborlaw:laborlaw_dev@tcp(127.0.0.1:3307)/laborlaw?parseTime=true&charset=utf8mb4&loc=UTC"
export LLM_API_KEY=$(grep -m1 '^LLM_API_KEY=' .env | cut -d= -f2- | tr -d '\r')

go run ./eval -dsn "$DSN" -mode keyword
go run ./eval -dsn "$DSN" -mode semantic
go run ./eval -dsn "$DSN" -mode hybrid
go run ./eval -dsn "$DSN" -mode rerank
```

**四条命令都必须显式带 `-mode`。** 不传时 `eval/main.go:51-58` 会去看 `RETRIEVAL_SEMANTIC` 环境变量：
该变量为真（本机 `.env` 里就是 `on`）时默认跑 `hybrid`，否则跑 `keyword`。
不写 `-mode` 就得出的结果无法说明自己是什么模式，本文件旧版把一次 `hybrid` 结果记成了关键词模式，就是这么来的。

`-semantic` 是 `-mode hybrid` 的旧写法别名（`eval/main.go:46`），新文档一律用 `-mode hybrid`。

## 已知天花板

- **E20（严重违反公司制度被开除，还有经济补偿吗）**：应答 `LCL-39`（过失性辞退无需补偿），
  keyword 档能进 @3，hybrid 档召回 `LCL-46`、rerank 档召回 `LL-28`（都是"一般情形应当补偿"那条）。
  这题本身有歧义——"被开除"既可以指过失性辞退（无补偿），也可以指违法解除（有赔偿金），
  两种读法对应不同条文。不是调权重能解的，需要换判例或问答语料才能让题目本身无歧义。
- **相邻条款的例外/特别规定**（E18、E25 这类）：向量算得出"主题相近"，算不出"这一条正好是例外"。
  rerank 已经把 E18、E25 从 ✗ 捞回 @3，但更大规模的同类问题仍会出现在新增用例里，
  见 `eval/README.md` 的维护约定。

### 退化的是哪两条

| 用例 | 组 | 问题 | 期望 | 517 条库 Top1 | 365 条库 |
|---|---|---|---|---|---|
| E01 | base | 公司不给我交社保，我能直接走吗 | LCL-38、LL-72 | LL-100（《劳动法》第一百条，责令限期缴纳） | @3 命中 |
| E43 | new-law | 上班时间跟同事打架受伤，能认定工伤吗 | WII-16 | WII-14（应当认定为工伤） | @3 命中 |

三次重跑（112 条、`-mode rerank`）结果完全一致，不是抖动。两条的 Top1 在 365 条库里也是
同一个条号（E01→LL-100、E43→WII-14），差别只在期望条文被挤出了 @3：

- **E01**：新增的 `SIL-63`、`SIL-86`（未按时足额缴纳→责令限期缴纳/补足、按日万分之五滞纳金）
  与既有 `LL-100` 一起，把「不交社保」这一问的候选池塞满"行政责令、滞纳金"类条文；
  中文重排指令让交叉编码器更贴字面同题，于是「劳动者可以解除」的 `LCL-38` 掉出 @3（@5 仍在）。
- **E43**：`SIL-38`/`SIL-41` 这批工伤待遇条文进池后，`WII-14`（应当认定）与 `WII-16`
  （不得认定）在重排里的相对分被拉开，否定型条文掉出 @3（@5 仍在）。「例外/否定」类条文
  （`WII-16`、`APL-4`、`LCL-70`）在重排里本来就长期吃亏，是已知天花板的一部分。

两条都是「加语料改变了候选池构成」的直接结果，不是能靠改判据或改 expected 消化掉的东西；
修它们必须动 `perLawCapHits`、重排窗口或指令，都属于本次明令禁止的临场调参。

### 回退与恢复

```bash
git checkout -- cmd/statuteseed/parse.go deploy/seed/statutes.json   # 语料退回七部
git revert --no-edit 4926968                                        # 12 条用例一起退（否则 expected 指向库里不存在的条号）
go run ./cmd/statuteseed -import                                    # 517 → 365 行
go run ./cmd/embeddingseed                                          # 365 条，37 批，13.2s
```

恢复后四档（365 条库、100 条用例）：`keyword` 57.0% / 70.0% / 零召回 7，
`semantic` 90.0% / 94.0% / 0，`hybrid` 81.0% / 89.0% / 0，`rerank` 98.0% / 99.0% / 0，
`base` 39/40——与回退前逐格一致，说明回退干净。

**回退时踩到的一件事：`embeddingseed` 只做幂等 upsert，不删孤儿向量。**
`statutes` 退回 365 之后 `embeddings` 里仍留着 152 条 LDA/SIL 的向量（`SELECT COUNT(*)`
= 517），必须手工清：

```sql
DELETE e FROM embeddings e LEFT JOIN statutes s ON s.id = e.owner_id
WHERE e.owner_type = 'statute' AND s.id IS NULL;   -- 清掉 152 条，剩 365
```

这条已补进 `deploy/runbook.md` 的入库段。

# eval —— 检索评测的最小集合

这个目录只做一件事：把「用户的口语提问」跑一遍检索，看期望的法条有没有进前 5。

为什么需要它：`internal/retrieval` 的词表和 SQL 一改，单看几条提问判断不出变好还是
变坏。模型答得"像"，可能只是它把没检索到的情形圆过去了；有没有拿到原文，得用同一批
用例、同一把尺子量。

## 怎么跑

```bash
# 需要库里有 596 条种子法条（没导过先导一次；`go run ./cmd/statuteseed -import` 会按 seed 全量重建）
go run ./cmd/statuteseed -import

TEST_MYSQL_DSN='laborlaw:laborlaw_dev@tcp(127.0.0.1:3307)/laborlaw?parseTime=true&charset=utf8mb4&loc=UTC' \
  go run ./eval

# 也可以显式传 DSN；-v 会额外打印每条召回的条号
go run ./eval -dsn '...' -v
```

没有 DSN 会直接报错退出（退出码 2），不会"静默跑 0 条"——评测跑出个空结果比不跑更误导。

## 指标

- `@3`：期望条号出现在前 3 条。模型实际最先读到的是这几条。
- `@5`：期望条号出现在前 5 条（`consult` 的默认检索深度）。
- 零召回：一条都没召回，模型只能回答"资料里没覆盖"。
- 分组：`cases.json` 每条可带可选 `"group"`，跑完按组各打一行；没写的老用例归 `base`。
  分组解决的是"总分把两类相反的情况平均掉"——某类问法整体失灵时总分只掉几个点。
- 一条提问有多个可接受依据（例如"不交社保"同时对应解除权与参保义务），
  命中其中任意一个即算命中：要求全中会把"答对但多引一条"判成失败。

## 怎么加用例

`cases.json` 里一条一个对象：

```json
{"id": "E101", "question": "用户的原话，尽量口语", "expected": ["LCL-38"], "group": "paraphrase"}
```

`expected` 里的 ID 必须来自 `deploy/seed/statutes.json`，**不许凭记忆写**：

```bash
# 库里到底有哪些条、正文是什么，用种子文件查
go run ./cmd/statuteseed -import -query '社保'

# 或直接看种子
python -c "import json;d=json.load(open('deploy/seed/statutes.json',encoding='utf-8'));print([s['id'] for s in d if '押金' in s['text']])"
```

写错 ID 的用例不会报错，只会永远 ✗——看起来像检索坏了，实际是用例坏了。

`expected` 的判据是"能回答这个问题的条文"，不是"含这个问题关键词的条文"。写的时候要能
用一句立法意图说清为什么是它；说不出这句，说明那条 `expected` 是照着跑分结果抄的。

## 词表口径（`internal/retrieval/keywords.go`）

`aliases` 的**键一律是词或短语**，不写成整句。原因很实际：键是拿来在用户提问里找的，
写成"没写工作岗位""哪些岗位""兼职有试用期"这种问句片段，等于把评测集的问法抄进字典——
评测分数会好看，换个说法一个词都提不出来，而答辩时被问"这批用例是不是照着自己调出来的"
就没法辩。2026-11-16 清掉了四条这类历史定向键：

| 原键（整句/问句片段） | 改成 | 依据 |
|---|---|---|
| `没写工作岗位` | `工作岗位` | 命中靠目标串"必备条款"，不靠键名长短 |
| `哪些岗位` | 并入 `劳务派遣` 的目标（三性） | 三性是派遣的限定条件，归属在派遣这个词上 |
| `兼职有试用期` | 删除，`兼职` 目标补 `非全日制用工` | LCL-70 原文就是"非全日制用工双方当事人不得约定试用期" |
| `社保和档案` | `社保转移` + `档案` | 一条问句拆成两个词，各自指向自己的条文 |

这批改动已经落地（`48dfdee`），代价也已经发生，不是预估：40 条口径下 keyword 档 hit@3
从 85.0% 降到 80.0%（E26、E30 各掉一条 @3，E30 仍在 @5），hybrid 与 rerank 两档没动
（92.5% / 97.5%）——生产链路走的是 rerank 那一档，所以这个代价换来的是词表可解释。

**泛化能力现在有数字了**：`paraphrase` 组 12 条是同一问题三种问法（各 4 组），
采纳中文重排指令与同法限流之后 rerank 档 **12/12**、semantic 10/12、keyword 8/12；
缺口行会点出哪条问法全灭（keyword 现在还有两处：未签合同的 E66/E67、违法辞退的 E68/E70）。
但那 12 条也只覆盖 4 个问题，要更强的证据得继续加同义问法，不是加新题目。

## 调参实验记录（2026-11-16，100 条用例）

100 条这把尺子第一次用来做单变量实验。四个实验：**A、C 回退，B、D 采纳**。
回退的也照实记——答辩问"你们怎么调的"，答案不是"调好了"，是"试了四个方向、
两个被数据否掉、两个被数据放行"——这比一个漂亮数字更能说明这套评测集在工作。

采纳后的 rerank 档：hit@3 **94/100 → 98/100（94.0% → 98.0%）**，hit@5 99/100 不变，
重排 p50 188ms → 185ms（n=100，机器噪声范围内）。keyword / semantic / hybrid 三档
逐条零变化——两次改动都只落在重排这一层。

跑法（每个实验都是这一条，只换 `-mode`）：

```bash
export DSN='laborlaw:laborlaw_dev@tcp(127.0.0.1:3307)/laborlaw?parseTime=true&charset=utf8mb4&loc=UTC'
go run ./eval -mode hybrid -dsn "$DSN" | tail -6
```

### 实验 A · RRF 两路加权 —— 回退

**改了什么**：`internal/retrieval/hybrid.go` 融合那两行原本都是硬编码 `1.0` 的分子，
引入 `rrfWeightKeyword` / `rrfWeightSemantic` 两个常量分别乘上去，`rrfK=60` 不动。
依据是 100 条里 `new-law` 组 hybrid 61.1% 而纯向量 100.0%、`exception` 组 37.5% 对
100.0%——关键词那路在否定式条文与新五部法上几乎召不回来，它给出的错误条目却和向量
那路的正确条目同权。

| 档 | 改前 | 关键词权重 0.5 | 关键词权重 0.3 |
|---|---|---|---|
| hybrid hit@3 | 81/100 81.0% | 79/100 79.0% | 79/100 79.0% |
| hybrid hit@5 | 89/100 89.0% | 90/100 90.0% | 90/100 90.0% |
| rerank hit@3 | 94/100 94.0% | 93/100 93.0% | 93/100 93.0% |
| rerank hit@5 | 99/100 99.0% | 97/100 97.0% | 97/100 97.0% |

**结论**：回退。采纳条件是 `hybrid @3 ≥ 90.0%` 且 `rerank @3 ≥ 94.0%`，两个权重都没过。

**为什么反而更低**（这条比数字有用）：降权压的不只是"关键词的错"，也压了"关键词的对"。
取证探针显示 E66「公司一直不跟我签劳动合同该怎么赔」的正确答案 LCL-82 只来自向量那一路
（关键词 20 条里根本没有它），压关键词权重对这类题毫无帮助；反过来 E24、E17 这类
"术语精确匹配才召得到"的题，正确答案只有关键词那路给，降权后被向量那路的错误条目挤下去。
0.5 与 0.3 结果逐条相同，因为权重只改变"两路之间"的相对次序，不改变"同路之内"的名次——
再往下调也不会出现新的排列。

### 实验 B · 重排指令中文化 —— 采纳

**改了什么**：`internal/llm/rerank.go` 的 `rerankInstruct`，从官方示例的英文网页检索
指令换成中文法律检索指令（判据落在"条文的规范内容能不能回答这个问题"，而不是字面重合）。

| 档 | 改前 | 改后 |
|---|---|---|
| rerank hit@3 | 94/100 94.0% | **96/100 96.0%** |
| rerank hit@5 | 99/100 99.0% | 99/100 99.0% |
| paraphrase 组 @3 | 11/12 91.7% | **12/12 100.0%** |

逐条：进 @3 的是 **E66**、**E99**，@5 无变化，没有一条掉出去。

**结论**：采纳（提交 `9caf13b`）。第一次跑这条改动记的是 95/100（进 E66、E99，掉 E17），
重放时是 96/100（E17 没掉）——同一个问题两次请求的重排分数不是逐位可复现的，
±1 条在噪声范围内。两个方向都过线（`@3 ≥ 96.0%` 或 `@5 ≥ 99.5%` 里 @3 那条），
而且 `paraphrase` 组满编 12/12：换一种问法不再掉，这是"泛化"最直接的证据。

采纳后的字符串就是仓库里这一行：

```go
// internal/llm/rerank.go
const rerankInstruct = "给定一个中文劳动用工问题，检索能够直接回答该问题的法律法规条文。"
```

### 实验 C · 候选池放宽 —— 原描述是空操作，改测窗口 30 后回退

**先更正一个事实**：`candidateK(topK)` 在 `topK=3` 时**已经返回 20**，不是 12。
`internal/retrieval/hybrid.go:104-108` 是

```go
if n := topK * 4; n > maxRerankCandidates {
    return n
}
return maxRerankCandidates
```

`topK*4=12` 不大于 20，所以走的是 `return maxRerankCandidates`。实测打印：

```text
candidateK(1) = 20
candidateK(3) = 20
candidateK(5) = 20
candidateK(6) = 24
candidateK(10) = 40
maxRerankCandidates = 20
```

所以"把候选池放宽到 20"这件事已经成立，没有可改的代码。

**改测什么**：真正的瓶颈不是 `candidateK` 而是融合后截断的窗口（`maxRerankCandidates`，
同一个常量管两件事）。探针显示 E99 的正确答案 LCL-63 在融合后正好卡在第 20 名之外
（0.01351 对第 20 名的 0.01370）——这是"被窗口切掉"，不是"被重排降权"。把窗口放到 30 测一遍：

| 指标 | 窗口 20 | 窗口 30 |
|---|---|---|
| rerank hit@3 | 94/100 94.0% | 94/100 94.0% |
| rerank hit@5 | 99/100 99.0% | 99/100 99.0% |
| 逐条 @3 | — | 进 E99，掉 E24 |
| 重排耗时 p50（n=100） | 188ms | 194ms（+3.2%） |

**结论**：回退。采纳条件字面上是过的（`@3 ≥ 94.0%` 且耗时增幅 ≤ 30%），但净收益为 0：
多进一条、多掉一条，只多付 3.2% 延迟。E99 的 LCL-63 被窗口切掉是真的，可它进来之后
E24 又被挤出去——说明窗口不是这批用例的主要瓶颈，**关键词那路的召回深度**才是
（LCL-63 压根不在 keyword 的 20 条里）。

### 实验 D · 按法律限流（同法最多占 2 席）—— 采纳

**要解决的问题**：重排把同一部法的相邻条一起打到高分，真正对题的那条被挤到 @3 之外。
探针在实验 B 之前量的三条退化就是这个形状：

```text
E66 重排前五  LCLR-5 0.7902  LL-98 0.7882  LCLR-6 0.7778  LCL-82 0.7714  LCL-81 0.7336
E75 重排前五  LCLR-34 0.7549  LCLR-6 0.7469  LCLR-7 0.7468  LCL-82 0.7405
E98 融合第 1、2 的 LCL-38、LCL-46 被压到第 7、第 8
```

《实施条例》的通则条对任何劳动法问题都"沾一点"，交叉编码器给它们整齐的 0.72~0.82 分。

**改了什么**：`internal/retrieval/rerank.go` 成功路径末尾加一层 `diversify`——
按 `Statute.Law` 分桶，同一部法在结果里最多占 `perLawCapHits=2` 席，扫一遍收满 topK，
剩下的按原顺序回填（输出与输入等长、集合不变）。三条降级路径（无 reranker / 重排报错 /
分数条数不符）保持原样：那三条本来就是放弃排序的兜底，在兜底上再削一轮只会更差。

**一处与指令不同的实现**：调用写成了 `clip(diversify(out, topK, perLawCapHits), topK)`，
而不是 `diversify(clip(out, topK), topK, perLawCapHits)`。原因：先 clip 到 topK，
被挤出去的那条已经不在切片里，限流函数只能空转——按字面写等于没改。限流必须作用在
完整排序上，clip 放到最后。

| 指标 | 实验 B 后 | 加限流 |
|---|---|---|
| rerank hit@3 | 96/100 96.0% | **98/100 98.0%** |
| rerank hit@5 | 99/100 99.0% | 99/100 99.0% |
| followup 组 @3 | 7/8 87.5% | **8/8 100.0%** |
| long 组 @3 | 5/6 83.3% | **6/6 100.0%** |
| 其余五组 @3 | — | 不变（base 39/40、new-law 18/18、paraphrase 12/12、exception 7/8、numeric 8/8） |
| 重排耗时 p50（n=100） | 184ms | 185ms（+0.5%） |

逐条：进 @3 的是 **E75**、**E98**，没有一条掉出去。累计（含实验 B）救回四条：
E66、E75、E98、E99；还剩两条 @3 未中——E20、E85。

**结论**：采纳（提交 `2ae8c9f`）。采纳条件是 `@3 ≥ 96.0%`、`@5 ≥ 99/100`、
`exception`/`numeric`/`paraphrase` 一条都不许掉、耗时增幅 ≤ 5%，实测 98.0% / 99.0% /
三组一条没掉 / +0.5%，一次过线，没有调 `perLawCapHits` 的必要。

**限流后 6 条 miss 的最终名次**（探针：融合 20 条候选 → 重排打分 → 排序 → `diversify`）：

```text
E20  LCL-39=第8   top3 LL-28, LCLR-25, LCL-46
E66  LCL-82=第2   LCL-10 不在候选      top3 LL-97, LCL-82, LCLR-6

```

读法：E66/E75/E98/E99 已经在 @3 里；E85 的 LCL-40 卡在第 4（只差一席），

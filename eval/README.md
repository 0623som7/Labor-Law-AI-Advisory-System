# eval —— 检索评测的最小集合

这个目录只做一件事：把「用户的口语提问」跑一遍检索，看期望的法条有没有进前 5。

为什么需要它：`internal/retrieval` 的词表和 SQL 一改，单看几条提问判断不出变好还是
变坏。模型答得"像"，可能只是它把没检索到的情形圆过去了；有没有拿到原文，得用同一批
用例、同一把尺子量。

## 怎么跑

```bash
# 需要库里有 365 条种子法条（没导过先导一次）
go run ./cmd/statuteseed -import

TEST_MYSQL_DSN='laborlaw:laborlaw_dev@tcp(127.0.0.1:3307)/laborlaw?parseTime=true&charset=utf8mb4&loc=UTC' \
  go run ./eval

# 也可以显式传 DSN；-v 会额外打印每条召回的条号
go run ./eval -dsn '...' -v
```

没有 DSN 会直接报错退出（退出码 2），不会"静默跑 0 条"——评测跑出个空结果比不跑更误导。

## 指标

- `@3`：期望条号出现在前 3 条。模型实际最先读到的是这几条。
- `@5`：期望条号出现在前 5 条（`consult` 的默认检索深度）。
- 零召回：一条都没召回，模型只能回答"资料里没覆盖"。
- 分组：`cases.json` 每条可带可选 `"group"`，跑完按组各打一行；没写的老用例归 `base`。
  分组解决的是"总分把两类相反的情况平均掉"——某类问法整体失灵时总分只掉几个点。
- 一条提问有多个可接受依据（例如"不交社保"同时对应解除权与参保义务），
  命中其中任意一个即算命中：要求全中会把"答对但多引一条"判成失败。

## 当前基线（2026-11-16，365 条库 / 七部法，100 条用例）

四档，`-mode` 一次一档。同库同用例，所以档与档之间的差值是可信的：

| `-mode` | 做了什么 | hit@3 | hit@5 | 零召回 |
|---|---|---|---|---|
| `keyword` | MySQL `LIKE` + 口语归一词表 | 57/100 = **57.0%** | 70/100 = 70.0% | 7 |
| `semantic` | 纯向量（`text-embedding-v3`，1024 维） | 90/100 = **90.0%** | 94/100 = 94.0% | 0 |
| `hybrid` | 关键词 + 向量，RRF 融合（k=60） | 81/100 = **81.0%** | 89/100 = 89.0% | 0 |
| `rerank` | RRF 后再过交叉编码器（`qwen3-rerank`） | 94/100 = **94.0%** | 99/100 = 99.0% | 0 |

按组（每档都会打出这两行；分组口径见上面的「指标」）：

| 组 | 条数 | keyword @3 | semantic @3 | hybrid @3 | rerank @3 |
|---|---|---|---|---|---|
| `base` | 40 | 32/40 80.0% | 35/40 87.5% | 37/40 92.5% | 39/40 97.5% |
| `new-law` | 18 | 5/18 27.8% | 18/18 100.0% | 11/18 61.1% | 18/18 100.0% |
| `paraphrase` | 12 | 8/12 66.7% | 10/12 83.3% | 10/12 83.3% | 11/12 91.7% |
| `followup` | 8 | 5/8 62.5% | 6/8 75.0% | 7/8 87.5% | 7/8 87.5% |
| `exception` | 8 | 0/8 0.0% | 8/8 100.0% | 3/8 37.5% | 7/8 87.5% |
| `numeric` | 8 | 4/8 50.0% | 8/8 100.0% | 7/8 87.5% | 8/8 100.0% |
| `long` | 6 | 3/6 50.0% | 5/6 83.3% | 6/6 100.0% | 4/6 66.7% |

三条读法，都是这批数出来的事实：

1. **`keyword` 档的诊断价值大于它的分数。** 57.0% 说明纯词面匹配在两类问法上基本失灵：
   `new-law` 27.8%、`exception` 0/8。条文写的是"不得认定为工伤""不享受当年年休假"，
   用户问的是"什么情况下不算工伤""哪些职工不享受年休假"——否定语义词表补不出来，
   只能靠向量那路。
2. **`hybrid` 在 100 条上低于 `semantic`（81.0% 对 90.0%）。** RRF 是等权融合，关键词那路
   漏掉的召回会一起带进融合结果，`new-law`（61.1% 对 100.0%）与 `exception`（37.5% 对 100.0%）
   两组最明显。生产链路走 `rerank`（94.0%），线上不受影响；但"融合一定优于单路"这个假设
   在这批用例上不成立，把它拉回来的是重排那一层。
3. **`paraphrase` 组的缺口单独打出来。** 同一问题三种问法、命中不一致的那几组会跟在
   `泛化缺口` 那行后面，下面是 `-mode keyword` 与 `-mode rerank` 的原始输出（其余两档的
   缺口行见各自输出）：

```text
# -mode keyword
泛化缺口（同题不同问法命中不一致）：
  expected=LCL-82,LCL-10 命中 E65 ｜ 未命中 E66,E67
  expected=LCL-87,LCL-48 命中 E69 ｜ 未命中 E68,E70
# -mode rerank
泛化缺口（同题不同问法命中不一致）：
  expected=LCL-82,LCL-10 命中 E65,E67 ｜ 未命中 E66
```

四条命令，逐条能跑出上表的数字（DSN 换成你自己的库；库不是 365 条则数字不可比）：

```bash
DSN='laborlaw:laborlaw_dev@tcp(127.0.0.1:3307)/laborlaw?parseTime=true&charset=utf8mb4&loc=UTC'
go run ./eval -mode keyword  -dsn "$DSN"
go run ./eval -mode semantic -dsn "$DSN"
go run ./eval -mode hybrid   -dsn "$DSN"
go run ./eval -mode rerank   -dsn "$DSN"   # 日志里 elapsed_ms 是单次重排往返，p50 ≈ 183ms
```

语义与重排两档要调 DashScope（`LLM_API_KEY` 等，见 `.env`）；没有 key 时这两档会降级成
关键词结果，跑出来的数会与上表不符——先看日志里有没有"语义检索降级"。

目标线是 **hit@3 75%**——与基线是两回事：基线随词表改动浮动，目标线只在
`eval/main.go` 里写一次（`goal3`）。现在 `keyword` 档 57.0% 低于它，其余三档高于它；
`keyword` 是诊断档、不是生产口径，所以这行提示不是回归。

**100 条与 40 条的数字不许直接相减。** 老 40 条只覆盖《劳动合同法》《劳动法》两部，
新 60 条里 18 条专问另外五部（工伤、年休假、派遣、女职工、实施条例）；分母换了，
两组数字的差是"题目变难了"，不是"检索变差了"。

## 历史基线（40 条，与上表不可比）

2026-11-16 扩到 100 条之前的口径，保留是为了能对上那几笔提交里的总结行：

| `-mode` | 做了什么 | hit@3 | hit@5 | 零召回 |
|---|---|---|---|---|
| `keyword` | MySQL `LIKE` + 口语归一词表 | 32/40 = 80.0% | 38/40 = 95.0% | 0 |
| `semantic` | 纯向量（`text-embedding-v3`，1024 维） | 35/40 = 87.5% | 37/40 = 92.5% | 0 |
| `hybrid` | 关键词 + 向量，RRF 融合（k=60） | 37/40 = 92.5% | 39/40 = 97.5% | 0 |
| `rerank` | RRF 后再过交叉编码器（`qwen3-rerank`） | 39/40 = 97.5% | 39/40 = 97.5% | 0 |

keyword 档是**诊断档**，不是生产口径——生产链路走 `-mode rerank`。40 条口径下这个数从
85.0% 降到 80.0% 是 `48dfdee` 把 `没写工作岗位`/`哪些岗位`/`兼职有试用期`/`社保和档案`
四组整句键改成词级键的代价：E26、E30 各掉一条 hit@3，两次都在「掉 1 条以内」的判定内，
rerank 档 39/40 未变。

40 条口径下丢分集中在三类，现在由三层分别兜住，答辩被问"为什么要有向量和重排"就答这个：

1. **归一目标在库里根本不存在**（违反 `keywords.go` 自己写的原则）：
   `"押金" → {"押金"}`，而《劳动合同法》第九条写的是"担保""收取财物"，全库没有
   "押金"二字 → E07 零召回。同类还有 `"仲裁" → {"劳动仲裁"}`：条文写的是
   "劳动争议仲裁委员会"，不含连续的"劳动仲裁" → E36 零召回。→ 由词表补全解决。
2. **口语词压根不在 aliases 里**：`未成年工`、`休息日`、`法定代表人变更`、
   `冒险作业` 这些说法没有任何键，提取不出检索词 → E33/E35/E38/E40 零召回。
   → 由词表补全 + 语义那路共同解决。
3. **每个词只取前 5 条、按词频排序**：`试用期` 在十九条里出现，第二十条（试用期工资）
   因命中次数少被挤出前 5 → E03 未命中。→ 由 RRF 扩候选（每路取 topK×2）与重排解决。

改完之后重跑本评测，把新的总结行贴进提交信息——基线只增不减才是"改好了"。

## 怎么加用例

`cases.json` 里一条一个对象：

```json
{"id": "E101", "question": "用户的原话，尽量口语", "expected": ["LCL-38"], "group": "paraphrase"}
```

`expected` 里的 ID 必须来自 `deploy/seed/statutes.json`，**不许凭记忆写**：

```bash
# 库里到底有哪些条、正文是什么，用种子文件查
go run ./cmd/statuteseed -import -query '社保'

# 或直接看种子
python -c "import json;d=json.load(open('deploy/seed/statutes.json',encoding='utf-8'));print([s['id'] for s in d if '押金' in s['text']])"
```

写错 ID 的用例不会报错，只会永远 ✗——看起来像检索坏了，实际是用例坏了。

`expected` 的判据是"能回答这个问题的条文"，不是"含这个问题关键词的条文"。写的时候要能
用一句立法意图说清为什么是它；说不出这句，说明那条 `expected` 是照着跑分结果抄的。

## 词表口径（`internal/retrieval/keywords.go`）

`aliases` 的**键一律是词或短语**，不写成整句。原因很实际：键是拿来在用户提问里找的，
写成"没写工作岗位""哪些岗位""兼职有试用期"这种问句片段，等于把评测集的问法抄进字典——
评测分数会好看，换个说法一个词都提不出来，而答辩时被问"这批用例是不是照着自己调出来的"
就没法辩。2026-11-16 清掉了四条这类历史定向键：

| 原键（整句/问句片段） | 改成 | 依据 |
|---|---|---|
| `没写工作岗位` | `工作岗位` | 命中靠目标串"必备条款"，不靠键名长短 |
| `哪些岗位` | 并入 `劳务派遣` 的目标（三性） | 三性是派遣的限定条件，归属在派遣这个词上 |
| `兼职有试用期` | 删除，`兼职` 目标补 `非全日制用工` | LCL-70 原文就是"非全日制用工双方当事人不得约定试用期" |
| `社保和档案` | `社保转移` + `档案` | 一条问句拆成两个词，各自指向自己的条文 |

这批改动已经落地（`48dfdee`），代价也已经发生，不是预估：40 条口径下 keyword 档 hit@3
从 85.0% 降到 80.0%（E26、E30 各掉一条 @3，E30 仍在 @5），hybrid 与 rerank 两档没动
（92.5% / 97.5%）——生产链路走的是 rerank 那一档，所以这个代价换来的是词表可解释。

**泛化能力现在有数字了**：`paraphrase` 组 12 条是同一问题三种问法（各 4 组），
rerank 档 11/12、semantic 10/12、keyword 8/12；缺口行会点出哪条问法全灭。
但那 12 条也只覆盖 4 个问题，要更强的证据得继续加同义问法，不是加新题目。

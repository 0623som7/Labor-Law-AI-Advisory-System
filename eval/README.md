# eval —— 检索评测的最小集合

这个目录只做一件事：把「用户的口语提问」跑一遍检索，看期望的法条有没有进前 5。

为什么需要它：`internal/retrieval` 的词表和 SQL 一改，单看几条提问判断不出变好还是
变坏。模型答得"像"，可能只是它把没检索到的情形圆过去了；有没有拿到原文，得用同一批
用例、同一把尺子量。

## 怎么跑

```bash
# 需要库里有 365 条种子法条（没导过先导一次）
go run ./cmd/statuteseed -import

TEST_MYSQL_DSN='laborlaw:laborlaw_dev@tcp(127.0.0.1:3307)/laborlaw?parseTime=true&charset=utf8mb4&loc=UTC' \
  go run ./eval

# 也可以显式传 DSN；-v 会额外打印每条召回的条号
go run ./eval -dsn '...' -v
```

没有 DSN 会直接报错退出（退出码 2），不会"静默跑 0 条"——评测跑出个空结果比不跑更误导。

## 指标

- `@3`：期望条号出现在前 3 条。模型实际最先读到的是这几条。
- `@5`：期望条号出现在前 5 条（`consult` 的默认检索深度）。
- 零召回：一条都没召回，模型只能回答"资料里没覆盖"。
- 一条提问有多个可接受依据（例如"不交社保"同时对应解除权与参保义务），
  命中其中任意一个即算命中：要求全中会把"答对但多引一条"判成失败。

## 当前基线（2026-11-16，365 条库 / 七部法，40 条用例）

四档，`-mode` 一次一档。同库同用例，所以档与档之间的差值是可信的：

| `-mode` | 做了什么 | hit@3 | hit@5 | 零召回 |
|---|---|---|---|---|
| `keyword` | MySQL `LIKE` + 口语归一词表 | 34/40 = **85.0%** | 38/40 = 95.0% | 0 |
| `semantic` | 纯向量（`text-embedding-v3`，1024 维） | 35/40 = **87.5%** | 37/40 = 92.5% | 0 |
| `hybrid` | 关键词 + 向量，RRF 融合（k=60） | 37/40 = **92.5%** | 39/40 = 97.5% | 0 |
| `rerank` | RRF 后再过交叉编码器（`qwen3-rerank`） | 39/40 = **97.5%** | 39/40 = 97.5% | 0 |

四条命令，逐条能跑出上表的数字（DSN 换成你自己的库；库不是 365 条则数字不可比）：

```bash
DSN='laborlaw:laborlaw_dev@tcp(127.0.0.1:3307)/laborlaw?parseTime=true&charset=utf8mb4&loc=UTC'
go run ./eval -mode keyword  -dsn "$DSN"
go run ./eval -mode semantic -dsn "$DSN"
go run ./eval -mode hybrid   -dsn "$DSN"
go run ./eval -mode rerank   -dsn "$DSN"   # 日志里 elapsed_ms 是单次重排往返，p50 ≈ 183ms
```

语义与重排两档要调 DashScope（`LLM_API_KEY` 等，见 `.env`）；没有 key 时这两档会降级成
关键词结果，跑出来的数会与上表不符——先看日志里有没有"语义检索降级"。

这个数字是**当前基线**（每轮实测的现状），目标线是 **hit@3 75%**——两者是两回事：
基线随词表改动浮动，目标线只在 `eval/main.go:218` 里写一次（`goal3`）。
现在四档都远高于 75%，所以正常情况下不会再打印「低于目标」那行提示。

口径提醒：这 40 条用例是照着真实提问写的，但词表历史上曾出现"把评测问句抄成字典键"的
定向映射（2026-11-16 已清理成词级键，见 `internal/retrieval/keywords.go`）。所以 hit@3
反映的是**这 40 条上的表现**，不等于跨表述泛化能力；换一批问法重测才是泛化。

历史上丢分集中在三类，现在由三层分别兜住，答辩被问"为什么要有向量和重排"就答这个：

1. **归一目标在库里根本不存在**（违反 `keywords.go` 自己写的原则）：
   `"押金" → {"押金"}`，而《劳动合同法》第九条写的是"担保""收取财物"，全库没有
   "押金"二字 → E07 零召回。同类还有 `"仲裁" → {"劳动仲裁"}`：条文写的是
   "劳动争议仲裁委员会"，不含连续的"劳动仲裁" → E36 零召回。→ 由词表补全解决。
2. **口语词压根不在 aliases 里**：`未成年工`、`休息日`、`法定代表人变更`、
   `冒险作业` 这些说法没有任何键，提取不出检索词 → E33/E35/E38/E40 零召回。
   → 由词表补全 + 语义那路共同解决。
3. **每个词只取前 5 条、按词频排序**：`试用期` 在十九条里出现，第二十条（试用期工资）
   因命中次数少被挤出前 5 → E03 未命中。→ 由 RRF 扩候选（每路取 topK×2）与重排解决。

改完之后重跑本评测，把新的总结行贴进提交信息——基线只增不减才是"改好了"。

## 怎么加用例

`cases.json` 里一条一个对象：

```json
{"id": "E41", "question": "用户的原话，尽量口语", "expected": ["LCL-38"]}
```

`expected` 里的 ID 必须来自 `deploy/seed/statutes.json`，**不许凭记忆写**：

```bash
# 库里到底有哪些条、正文是什么，用种子文件查
go run ./cmd/statuteseed -import -query '社保'

# 或直接看种子
python -c "import json;d=json.load(open('deploy/seed/statutes.json',encoding='utf-8'));print([s['id'] for s in d if '押金' in s['text']])"
```

写错 ID 的用例不会报错，只会永远 ✗——看起来像检索坏了，实际是用例坏了。
